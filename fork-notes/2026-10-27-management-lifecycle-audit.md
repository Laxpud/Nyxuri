# 配置管理生命周期审查与修复方向

> 审查与冻结日期：2026-10-27。基于 Ubuntu 26.04.1 本机和 `ubuntu` 分支
> `d24374f7af3a95c6e9b1b41885dca306a5966cff`，记录管理机制审查证据与待讨论的修复方向。
> 本文不表示方案已获实施授权，不替代正式契约，也不承诺穷尽所有运行问题。

## 范围与证据口径

用户要求先分析其他管理机制及运行兼容问题，再讨论解决方案。本轮检查了
`on / update / preset / off / snapshot / rollback / uninstall` 的文件与账本路径，
以及 Noctalia 模板、Fish 插件、Fcitx 钩子、Shell 切换和 XDG 路径的关联。
此前命令接管结果及已复现问题见 [本机接管记录](2026-10-27-local-config-adoption.md)。

- **实测**：只读查询或应用自身检查在本机返回的结果；此前已执行的接管另引用旧记录。
- **源码确认**：已找到触发条件和确定的调用路径；没有在真实用户目录执行破坏性复现。
- **设计限制**：代码与现行契约可能一致，但不满足“配置只靠 Nyxuri 命令可靠管理”的目标，需先决定语义。
- **待验收**：涉及真实切换、关停、错误注入或其他桌面环境，本轮没有执行。

未修改实现或本机配置，未执行 `off`、`rollback`、`uninstall`、Shell 热切换或完整更新部署，
未新增测试，也未运行全量测试或沙箱部署。自研 Shell 的全部 QML 功能、外部服务及所有硬件组合不在本次覆盖范围。

## 新发现的管理问题

### M01 — Vault 恢复可能删除 off 刚刚保留的外来文件（优先修复）

**源码确认，并有本机文件布局证据。**

[transaction.py](../nyxuri/kernel/transaction.py) 的 `_vault_archive()` 按路径保存 Custom，
`_vault_restore()` 却按 Vault 顶层条目恢复：目标存在时先 `remove_path(target)`，再移动整个条目。

本机 Fish 的 `conf.d/__custom__/` 会归档成 `vault/fish/conf.d/__custom__/`，
而 `conf.d/autopair.fish`、`conf.d/fzf.fish`、`conf.d/nvm.fish` 不在受管快照或 preserve 范围内。
`off` 会将这些外来文件留在原地；再次 `on` 恢复 Vault 的 `conf.d/` 时，却会先删除整个实机
`conf.d/`。即使钩子随后重装部分固定插件，也不能恢复所有个人文件。

**修复方向**：按文件递归合并 Vault；同名新旧内容不同则保留两份并报告，不能通过替换父目录吞掉幸存文件。
归档内容在恢复提交成功前不应被消费，恢复失败须保留可重试副本。

### M02 — off 不保护普通受管文件中的个人改动

**源码确认；同时是需要重新决定的保留策略。**

`_vault_archive()` 只保存 `__custom__` 和 manifest `preserve`；`_wipe_unit()` 对账本中的文件
按路径删除，不比较当前哈希。用户直接改过的 `config.fish`、`fish_plugins` 或 `starship.toml`
仍可能被删除；单文件单元没有 Vault 恢复路径。`on` / `off` 本身也没有创建完整快照。

当前契约只明确承诺这些指定保留槽，因此不能将所有删除都称为实现违约。但这与普通更新会保留个人改动的
行为不同，用户容易把“更新安全”理解为“停用也安全”。

**修复方向**：停用前按账本识别用户修改并归档，包括单文件单元；默认只删除未修改的受管产物。
明确区分普通停用与显式丢弃个人改动，不让用户依赖手工备份兜底。

### M03 — preset apply 与单元事务脱节

**源码确认。**

[desktop/presets.py](../nyxuri/desktop/presets.py) 的 `apply_preset()` 直接替换目录、写活动预设；
没有更新 `units.<id>.files` 或单元记录的 `preset`，也不检查单元是否启用。
[deploy/preset.py](../nyxuri/deploy/preset.py) 的 `write_active_preset()` 更新的是顶层 `presets` 字典与 `.active` 文件。

- 切换后配置已经改变，但单元账本仍对应旧内容；doctor 可能误报漂移，后续 update 可能把命令部署的内容当作个人修改保留。
- 停用单元仍可以通过 `preset apply` 或 `preset part` 写出配置，破坏停用状态。
- `preset apply` 没有启用 carry；只有 Custom/preserve 被保护，用户额外放入的普通文件可能随目录替换丢失。
- `_is_deployable_app()` 将单文件 Starship 也视作可使用预设的应用，`apply_preset()` 却按目录名拼接目标。
  `preset starship apply default` 的代码路径会写入 `~/.config/starship/`，而非真正的 `starship.toml`。
  契约声明 target 单元不支持预设，但入口没有正确拒绝。

**修复方向**：预设与零件切换作为统一事务的具体操作，先验证单元类型、启用状态和源，再同步提交内容与账本。
默认保留外来文件；需要舍弃旧预设产物时仅清理已确认归属的文件。

### M04 — on --preset 在新安装、无效名称和失败时的语义不可靠

**源码确认。**

`unit_on()` 先 `write_active_preset()`，然后调用批量部署的 `resolve_preset_src()`。
后者原用于更新恢复：目标目录不存在且 active 非 default 时，回退 default。
因此在全新配置目录执行 `on kitty --preset transparent`，显式选择可能被当作“旧目录丢失”而重置。

若目标目录已存在但预设名不存在，解析会返回冻结；`_phase_atomic_deployment()` 只 `continue`，
未把该单元记入失败列表。上层仍可能执行钩子、快照旧文件并记为 enabled，活动预设却指向不存在的名字。
文件部署失败时，提前写入的 active 也未撤回。

**修复方向**：显式选择使用直接预设查找，不能混用更新的丢目录恢复规则；在所有写入前验证名称、类型及源。
区分 deployed / skipped / failed，只有实际完成才提交 active 与单元状态。

### M05 — snapshot / rollback 不能恢复一致的管理状态

**源码确认。**

[state/backup.py](../nyxuri/state/backup.py) 的快照只复制 `discover_config_items()` 返回的配置对象，
不保存单元账本、活动预设与零件选择、Vault 或钩子的跨目录产物；merge 单元也不在该列表中。
`rollback_configs()` 只恢复文件，不更新账本或活动选择，也不处理快照中缺席的后来新增单元。

因此“配置恢复了”不等于“管理状态恢复了”；旧文件配上新账本会造成漂移误判或下一次更新重新应用错误预设。
目标路径迁移后，旧快照还会按当前 manifest 解释，缺少历史目标位置元数据。

**修复方向**：为快照增加版本、恢复范围、原部署目标、所选单元状态和预设元数据。
恢复选定单元时一起恢复并验证内容与对应账本，不能盲目覆盖整份全局 state.json。
旧快照应明确标为“仅文件”，不能冒充完整事务恢复点。

### M06 — uninstall 仍有绕过归属和账本的旧路径

**源码确认。**

[state/uninstall.py](../nyxuri/state/uninstall.py) 先对启用的 hook 单元执行 `off`，之后才归档剩余配置目录。
结合 M02，受管文件中的普通修改可能在归档前已被删掉。随后 configs 分支按所有可部署目录整目录移除，
不按账本逐文件归属处理；其范围包括未启用配置。

无 hook 单元的账本没有随目录删除而变为 disabled；默认卸载又保留 state。
重新执行 `on kitty` 等命令会遇到 already-enabled，无法恢复已删除的配置。
壁纸清理仍依赖旧 `.nyxuri-managed.json` 标记，而当前 merge 单元记账在 ledger，存在残留路径。

**修复方向**：统一从已管理单元生成卸载计划，先完成备份，再执行同一停用事务。
未登记目录默认不动；配置归档、外来文件保留、状态更新和跨目录产物清理必须一致。
旧标记只能用于明确的兼容迁移，不能替代当前账本。

### M07 — 钩子失败后被记为终态，普通命令没有重试路径

**源码确认；非致命 WARN 本身是现行契约，问题在缺少可恢复状态。**

`unit_on()` / `unit_off()` 在钩子失败后仍写 enabled / disabled，并返回 `Step(ok=True, detail=hook-failed...)`。
普通 `on` 对已启用单元立即返回；`off` 在已停用且目录不存在时也提前返回。
所以配置已复制但 GTK 渲染失败，或配置已删但显示管理器恢复失败，之后都可能无法用同一命令重试。
更新工作流还忽略 `replay_enabled_hooks()` 的返回列表。

**修复方向**：区分可延迟的会话动作与必须成功的系统动作，持久保存未完成阶段并提供幂等重试。
关键 hook 失败不能报告完整成功，不能让错误状态阻断下一次恢复。已启用不应等于无需检查健康状态。

### M08 — 跨单元依赖和主题输出不受启用状态约束

**源码确认，并有本机配置证据。**

当前文件类单元的 `dependencies` 全为空，但 [Noctalia 配置](../units/noctalia/noctalia-config.toml)
引用 theme 单元提供的 GTK、Niri、Mango 和 palette 模板，也引用 Fcitx 的皮肤模板。
全新机器单独 `on noctalia` 没有机制保证这些输入存在；本机已有这些资源，不能替代新安装验收。

输出也没有按接收单元状态筛选：Mango 未启用，Noctalia 仍配置了
`~/.config/mango/noctalia.conf` 输出，本机该目录只有这个文件。
Kitty、Niri、Fcitx 等单元停用后，后续模板渲染仍可能重建其文件。未实机执行关停后渲染复现。

**修复方向**：声明真正必需的模板依赖；可选消费者按启用状态生成渲染清单。
停用时先解除生产者输出，再撤回文件。不要通过强制启用全部消费者解决依赖问题。

### M09 — 单元生活区外的文件缺少可靠归属证明

**源码确认。**

[Noctalia 清理钩子](../units/noctalia/hooks/remove-gtk-css) 只凭普通 CSS 文本
`@define-color accent_bg_color` 判定 `gtk.css` 归己所有，并无条件删除 `gtk-dark.css` 符号链接。
其他主题或用户文件也可能满足该条件。Fcitx 皮肤撤回也主要按固定文件名删除，而非核对最后写入内容。

此外，[Shell 切换](../nyxuri/desktop/shell_switcher.py) 的 `ensure_compositor_gateway_scripts()`
会把 Niri 的两个网关脚本直接对齐源码，不检查个人改动或账本，不通过部署原语；失败的切换也可能已经改动脚本。

**修复方向**：跨目录写入记录原值、最后写入内容和生产者；清理前核对归属，保留后续个人改动。
网关脚本更新纳入 Niri 的正常事务。共享 GTK 输出需协调当前生产者，不能用通用文本标记猜归属。

### M10 — merge 单元没有完整更新路径

**源码确认；补充此前壁纸误报。**

`discover_deployable_apps()` 排除 merge 单元；update 随后仅调用
`enable_theme_unit()` / `enable_wallpapers_unit()`，最终都是 `unit_on()`。
已启用单元会直接返回，因此上游 theme 模板修改或新增文件不会通过这条路径更新。
即使再次进入 merge 部署，它也只补缺失文件，不能升级未经用户修改的已有受管模板。

**修复方向**：共享目录也要有按文件归属执行的 refresh：更新未改动的受管文件、补入新文件、保留个人文件。
doctor 只比较登记文件；`--force` 也不能扩大成覆盖整个共享目录。

### M11 — 源码删除或更改单元布局后缺少迁移机制

**源码确认；当前本机没有已删除单元记录。**

`audit_units()` 合并蓝图与账本 ID 后，对每个 ID 无条件调用 `registry.load_unit()`。
若上游删除了一个已登记单元，整个审计会抛 KeyError；CLI 捕获后返回错误，而不是展示其他正常单元。
`off` 同样依赖当前 registry，无法从旧账本独立撤回该单元。

部署目标只从当前 manifest 读取；账本文件路径是相对路径，缺少历史部署目标。
这也是 Fcitx 不能直接修改 target 再 off 的根本原因。

**修复方向**：增加版本化部署元数据，记住已落地目标与归属；保留可审计的 orphan 状态和明确迁移步骤。
迁移必须先识别旧布局并备份，不能把新目标路径当作旧单元的删除位置。

### M12 — 损坏或不可读账本被当作空账本

**源码确认；本机账本正常，未注入损坏。**

[ledger.py](../nyxuri/kernel/ledger.py) 的 `read_ledger()` 对读取、解析错误统一返回 `{}`，
`update_ledger()` 随后可能基于空状态写回。读取失败与首次安装没有区分；锁获取异常时也继续写入。
这会丢失归属信息，后续 `on` 可能把已有配置按首次接管处理。

**修复方向**：缺失账本与损坏账本分开处理；损坏或无法加锁时拒绝写操作，保留原件并提供恢复入口。
只读诊断可以降级展示，但不能把错误状态当成可安全部署的空白环境。

## 运行兼容及路径问题

### R01 — 自研 Shell 预检漏掉必需运行时

**本机只读实测**：`preflight_shell('nyxuri-shell')` 返回成功，入口为仓库的 `shell/nyxuri-shell`，
但 `qs` 和 `quickshell` 均不在 PATH。预检只核对包装脚本存在与可执行，未接入平台依赖清单。
包装脚本实际启动才检查 `qs`；热切换流程此时可能已退出旧 Shell，之后才发现失败并尝试回滚。
本轮未真正切换 Shell。

**修复方向**：停止旧实例前检查必需运行时及基础 QML 导入；可选功能缺席单独降级。
自研 Shell 仍属实验性范围，不能拿 Noctalia 正常运行来替代其验收。

### R02 — 配置目录、数据目录和图片目录口径不统一

**源码确认；本机当前默认路径未触发。**

`Environment` 固定使用 `~/.config` 与 `~/.cache`；Fcitx 钩子也硬编码用户数据和状态目录，
并未完整遵循 XDG 路径。另一方面启动器保留 HOME 内的自定义 XDG 路径，外部应用可能按另一套路径读写。

壁纸单元目标固定为 `~/Pictures/Wallpapers`，Noctalia 渲染与卸载则使用 `xdg-user-dir PICTURES`。
图片目录被本地化或自定义时，部署、读取、清理可能落在不同位置。本机当前三者同为 Pictures。

**修复方向**：统一路径解析，覆盖引擎、模板、钩子和桌面脚本；或明确拒绝尚不支持的非默认布局。
不能部分接受环境变量后静默写入另一目录。

### R03 — 目前可确认的运行结果与未覆盖范围

- Niri 的实机配置可通过 `niri validate`；仅提示 optional `noctalia.kdl` 不存在，不把这一可选提示算作致命错误。
- Noctalia 为 v5.3.0，实际 CLI 提供当前模板使用的主要命令；这里只检查接口，不代表所有交互都已验收。
- Kitty 0.45.0 的两条滚轮绑定警告、Fcitx 目标路径错误及 Portal 跨桌面路由风险沿用此前记录。
- 当前 Noctalia 引用的模板输入均存在；这只是已有机器的状态，不能证明首次单元安装会正确供给依赖。
- 真实双屏截图、输入法长期稳定性、Plasma/Niri 来回登录、显示管理器切换、热重载及自研 Shell 全功能仍需单独验收。
- 依赖包存在不等于参数、配置格式和运行时 ABI/QML 兼容，后续应以实际消费该依赖的程序做能力检查。

## 不应误称为缺陷的现行边界

脏开发仓库跳过 update 是保护本地修改的机制；问题是缺少清晰的“只部署当前源码”入口，以及自动化不能只看退出码。
`install config` 的复制模式、`install full` 不自动登记所有新单元、用户预设不自动合入默认配置变化，
都是当前已写明的语义。它们与统一管理目标存在使用上的落差，应调整接口或说明，不能仅凭命名判断实现错误。

已查看的测试主要分别验证复制、active 选择、Vault 和账本字段；这些单路径检查不能替代跨命令生命周期验收。
本轮没有将“测试文件存在”当作上述组合场景已经通过的证据。

## 建议的修复顺序（待讨论，不代表开始实施）

### 第一阶段：先守住数据和结果状态

优先修 M01、M02、M06、M07、M12：停用前归档修改、Vault 无损合并、卸载先备份后删除、
关键阶段失败可重试、损坏账本停止写入。同时修复 M04 的输入预检和假成功路径。
每项先形成可独立审阅的小改动，不先重写整个部署引擎。

### 第二阶段：统一命令对文件和账本的提交

在内核中提供共同的“计划 → 预检 → 暂存/备份 → 文件提交 → 账本提交 → 运行时动作”流程，
让 on、配置 refresh、preset、rollback、off、uninstall 共用；运行时动作根据严重程度进入可重试的未完成状态。
必要时保存最小恢复记录，避免进程中断后只改了一半状态。

update 只处理启用且平台支持的单元；拉取源码与应用当前源码分开，并明确未变化、已跳过、部分完成和失败。
新依赖的安装仍需在变更计划中披露。具体 CLI 参数名另行确定，不通过私自调用内部函数替代用户命令。

快照和账本增加版本化元数据以支持 M05、M11；需要正式更新五字段契约时显式设计迁移，
不能直接给现有账本塞未经约定的字段，也不能重新计算所有现有文件哈希来抹平归属差异。

### 第三阶段：整理单元关系、共享目录和外部产物

处理 M08—M10：必需依赖入图，可选模板输出跟随消费者启用状态；共享目录按受管文件更新。
每个跨目录写入有明确生产者、原内容和最后写入身份，切换及清理时保护用户后续修改。

Fish 固定插件与个人插件分开维护，用户插件清单不应被模板接管，也不应因此让整个 hook 拒绝执行。
Fcitx 目标修复与旧布局迁移一起设计，复用统一归属机制；不以“整个 fcitx5 目录都是自己的”来处理共享目录。

1. 空目录和已有定制两种 `on`；显式预设不会被忽略，无效预设零写入。

## 2026-10-27 讨论补充：部署约束与停用策略

本节记录审查后的用户补充及建议，不改写前面的审查事实；尚未修改实现。

### 用户明确要求：Portal 支持多会话并存

- 按 WM/桌面会话生成专用规则，默认只部署当前平台受支持桌面的专用配置。
  判断范围应覆盖用户启用的多个会话，不只检查执行命令时的当前桌面。
- 默认不生成通用 `portals.conf`，不把 Niri 的路由当成全机器默认路由，也不修改系统提供的其他桌面规则。
- 已有通用配置必须先识别来源：当前账本、历史部署证据及内容是否被修改。
  同名或内容类似默认模板，不能单独作为自动删除的归属证明。
- 用户自行维护或来源不明的通用配置保留并报告；确认属于旧部署且需要迁移的文件，迁移前也须备份。
  规则优先级和后端选择要按实际会话验证，不能仅以文件存在作为生效依据。

### 用户接受的方向：冲突可强制覆盖，但先自动备份

- 发现冲突先披露受影响文件与行为；允许用户显式选择强制采用模板。
  强制只作用于已展示的冲突范围，其他外来文件保留。
- 覆盖前备份原配置及相关归属、预设和恢复元数据；备份失败则停止覆盖。
  强制覆盖所需备份不能被现有安装菜单的普通“备份”选项关闭。
- 备份集中放在 Nyxuri 状态/备份区域，采用唯一版本目录；不在应用生效目录随意生成可能被加载的 `.bak` 文件。
- 对 Fish 等会运行钩子的操作，备份范围覆盖钩子将修改的插件文件和状态，不能只保存 `fish_plugins` 一份清单。
- 备份用于恢复原状，不能把被覆盖的个人内容重新登记成仓库模板的基线。
  该方向允许用户采用默认插件集合，但不替代“保留个人插件时 hook 能正常工作”的修复。

### 对安装交互界面的影响

现有主菜单布局不必重做，但行为和反馈需要同步：安装/更新的候选范围、冲突列表、备份位置、
强制采用模板选项、部分完成与重试、停用时的归档摘要。
`installer/menus.py` 负责组件选择，`installer/workflows.py` 执行工作流，
`tui.py` 的工坊调用相同的单元事务并与 CLI 共用 `format_steps()`。
修复不能仅接入 CLI，留下交互安装、更新或预设入口继续使用旧路径。

### 停用判定方式（后续讨论已确认，尚未实现）

主要依据应是“上一次由 Nyxuri 实际部署成功的内容”，包括已选择的预设、路径渲染和受管钩子产物；
不是仓库此刻的原始模板。否则上游模板更新、预设切换或 `/home/user` 渲染都可能被误认作个人修改。

| 文件情况 | 建议停用行为 |
| --- | --- |
| 受管文件与上次部署基线一致 | 可撤回，记录移除结果 |
| 受管文件与基线不同 | 先归档当前内容和归属信息，成功后才从生效区撤回 |
| Custom / preserve | 按原约定归档，无需靠模板差异推断是否属于用户 |
| 外来文件、来源不明文件 | 默认留在原地并报告，不因位于同一目录就删除 |
| 文件已经缺失 | 记录缺失状态，不把缺失当成“未经修改” |
| 运行时生成文件 | 依据生产者与最后写入身份处理，不能把每次自动配色都判为个人修改 |

更新时可以使用三方比较：上次部署基线、当前文件、即将部署的新模板/预设。
停用本身主要需要比较前两者。哈希足以识别是否变化，但要展示差异或完整恢复，还需保留对应内容或可重建的来源版本。
基线不能因用户修改而改记为当前内容；也不能丢弃历史归属，导致下次无法判断应保留还是撤回。

重新启用时，逐文件恢复归档并处理与新模板的冲突；禁止用整个目录覆盖恢复。
在普通停止使用单元的过程中，不提供静默删除个人修改的默认行为。
