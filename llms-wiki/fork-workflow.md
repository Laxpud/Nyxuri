# 本 fork 的个人协作规则

> 本页是 `Laxpud/Nyxuri` 的个人协作规则源，集中维护分支职责、文档分工、同步和 PR 授权边界；脚本用法见 [PR 分支指南](pr-branches.md)。

上游为 `ech678/Nyxuri`。开始 Git 操作前核对当前工作目录、分支、工作区改动和远程地址，
区分本地引用缓存与实际远程状态。

## 分支职责

| 分支 / 远程 | 用途与边界 |
| --- | --- |
| `upstream` | 原作者仓库，用于获取更新和作为 PR 的目标；不向其直接推送 |
| `origin` | 用户自己的 fork，开发分支和个人文档推送到这里 |
| `main` | 同步上游 `main`，不加入 Ubuntu 适配、个人文档或本 fork 专属工具的提交；跟踪 `origin/main` |
| `ubuntu` | 日常开发分支，保存 Ubuntu 兼容改动及个人文档、工具；跟踪 `origin/ubuntu` |
| `codex/pr-*` | 从目标上游提交准备的 PR 分支，只包含本次准备贡献的改动，推送到 `origin` 后向上游 `main` 提 PR |
| `codex/backup-*` | 操作前的恢复点，不继续开发、不作为 PR 来源；未经用户要求不删除 |

## 同步与个人文件

- **同步上游**：先获取上游并检查提交关系。`main` 优先快进；上游改写历史时保留恢复点，
  说明差异再按用户授权处理。`ubuntu` 已有独立提交后，更新必须保留兼容改动、个人文件及未提交内容，
  不得为了“与 main 一致”直接重置或强制覆盖；优先合并上游更新，改写已推送历史前取得明确授权。
- **个人文件**：允许提交到 `ubuntu` 和自己的 fork；用 `.pr-exclude` 指定不贡献给上游的路径，
  不依赖 `.gitignore` 隐藏已跟踪文件。清单为空就是没有排除规则，不能声称个人内容已自动过滤；
  未经用户要求不填充清单。规则语法和排除行为以 [PR 分支指南](pr-branches.md) 为准。
- **规则维护**：本 fork 的个人约定统一修改本页，根目录 `AGENTS.md` 只保留读取指引，
  不重复维护完整规则。同步上游 `AGENTS.md` 时接纳上游项目规范，并在 `ubuntu` 中保留指引；
  发生冲突时逐项合并，不整文件覆盖。若规则含义冲突，指出文件路径和原句，按用户明确指令处理。
- **跨分支使用**：本页随 `ubuntu` 管理；不向保持上游原样的 `main` 注入个人规则。
  在不含本页的分支或独立工作区开启新对话时，需要另行向 AI 提供这些约定，不能假定它自动继承。

## 文档分工与开发记录

- **先读原有规则**：修改已有文档或新增文档前，先读所在范围的 `AGENTS.md`、文档入口与
  对应规范，确认读者、用途和维护方式。修改 wiki 时先按 [llms.txt](llms.txt) 路由，
  遵循 [文档宪章](docs-charter.md) 和相关主题页；README、ROADMAP、CHANGELOG 等
  也按各自规则处理，不把任意 Markdown 文件当作开发日志入口。新增页同样遵循原有
  分层、命名与索引要求，不能通过新建页面绕过这些约束。
- **正式文档的内容准入**：内容必须同时符合目标文档原有职责，并且是维护现行契约
  或使用方法所必需的；仅仅“可复用”或“能够再次执行”不足以成为写入理由。
  契约页中的验收方式、测试规范页中的通用要求和开发指南中的调试步骤，按原职责维护；
  为一次适配任务设计的验证方法仍属于个人记录，不能只删去“本机”“本轮”或改标题
  就转成正式指南。代码行为、命令或依赖变化时仍须同步对应正式文档，不能只留下
  个人日志链接。一个现行事实只维护一处，其余位置按需引用；ROADMAP 简记交付与规范状态。
- **个人记录另存**：需要保留的本机环境、软件源调查、排查尝试、验证过程、备份及
  恢复操作放在仓库根目录的 [fork-notes/](../fork-notes/README.md)。这是本 fork 的
  个人历史记录区。任务专用的验证计划、环境准备、命令清单和验收矩阵也放在这里，
  不限于执行结果；原仓库测试规范页承担的通用规则仍留在原位置。
  项目正式历史仍遵循原有 archive 规则，不把个人记录塞入上游归档。
  `notes/` 继续作为原仓库定义的忽略草稿区，不承担需要在 fork 中保存的记录。
- **按需记录，避免另建一套文档体系**：文件使用 `YYYY-MM-DD-topic.md`，注明记录日期、
  来源与适用环境，保留有价值的证据、结论边界和恢复方法，不保存凭据或整份机器配置。
  完成记录标明冻结日期，保留当时结果；后续更正注明日期，不追认旧记录为当前状态。
  不自动为每次操作写日志，也不在此另建 ROADMAP 或重复维护现行契约。
- **只留必要入口**：根 `AGENTS.md` 继续只路由到本页，本页链接开发记录目录；
  `fork-notes/README.md` 只列已有记录，不复制本页规则。正式指南不依赖个人记录才能
  完整使用；记录可以引用正式文档，不逐篇加入 `llms.txt` 或正式指南。
- **贡献时排除个人内容**：`fork-notes/` 通过 `.pr-exclude` 整目录排除，必要的入口
  链接只留在已有的 fork 专属文档或受过滤的入口中。检查 PR 时同时检查链接目标，
  不把个人目录过滤后的断链带给上游；入口整文件排除时，还须补齐应贡献的正式文档
  路由，避免一并遗漏。不要依赖 `.gitignore` 隐藏已跟踪内容。

## PR 与授权

- **准备 PR**：先阅读 [PR 分支指南](pr-branches.md)，运行
  `python3 tools/prepare-pr.py --dry-run` 展示包含与排除的路径；不要直接将混有个人文档的 `ubuntu` 整体提 PR。
  只有用户要求生成 PR 分支时才使用 `--create`；使用独立 worktree，不改动日常开发工作区。
- **提交与发布**：生成 PR 分支只代表准备好待审阅内容，不代表允许提交、推送或创建 GitHub PR。
  按用户明确授权执行相应步骤；只暂存本轮相关文件，提交前检查暂存差异，提 PR 前检查完整分支差异。
- **汇报**：分别说明本地分支、远程分支、暂存/提交/推送状态。不能把本地同步或预览成功说成远程更新完成。

## 检查方式

文档整理或迁移后，逐份检查本次涉及的文档及其改动段落：内容是否符合原有职责、
是否还有同类过程性内容、现行事实是否重复维护。同步核对标题、页首定位、索引描述、
相对链接与“上文／下文”等章节引用；迁移记录保留日期、证据和结论边界，不把历史
结果改写成当前承诺。不能只做关键词替换或链接检查，就判定迁移完成。

调整本页后运行现有文档契约检查，确认入口和索引链接有效；在实际 Git 操作前后核对分支、
工作区及差异是否符合以上职责。结构检查不能代替上述内容审阅，也不等于已执行或验证
同步、提交与 PR 操作。
